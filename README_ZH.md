# GnptHooks

简体中文 | [English](README.md) | [AI 协作文档](README_AGENT.md)

## 📖 介绍

**GnptHooks** 是一个面向 **AMD** 平台的 Windows（Windows 10 x64）内核函数钩子框架，以 Type-1 hypervisor 形态实现（AMD SVM + 嵌套分页）。

它通过虚拟化正在运行的系统，利用**每核双 NPT 视图**拦截函数执行——你的驱动可以钩取任意内核函数，**不修改原始内存的任何一个字节，且稳态下每次命中零 VM-Exit**。实测：物理机上累计 460 万+ 次拦截，NPF exit 计数器全程钉在每核一例。

> **使用 AI 助手（Copilot / Claude / GPT 等）参与本项目的二次开发？** 请先阅读 [README_AGENT.md](README_AGENT.md)——它包含本项目大量**反直觉的安全设计与红线约束**（含全部蓝屏判例）。跳过它直接改代码极可能引入蓝屏级缺陷。

> **Intel 机器？** 本项目是 GeptHooks（Intel VT-x/EPT）的 AMD/SVM 姊妹项目。两者为独立项目、零符号交集；设计互相参照，代码不共享。

## ✨ 三种钩子模式

按目标逐个选模式（安装时 `Hook.Flags`），三者可同机并存：

| | 普通模式（CodePage） | TRANSPARENT（DR） | NX-FENCE |
|---|---|---|---|
| 标志 | `0` | `HOOK_TRANSPARENT` | `HOOK_NXFENCE` |
| 机制 | NPT 视图影子页 | 硬件执行断点（DR0-3） | 页级 NX + 返回时重武装 |
| 读透明 | 否——影子视图可读 | **结构性**（原页恒等不动） | **结构性**（两视图皆原始字节） |
| PatchGuard 覆盖目标 | 禁用（0x109 蓝屏） | 安全 | 安全 |
| 稳态每次调用 exit 数 | **0** | 1 | 2 |
| 容量 | 每页一个（首匹配） | 每核 ≤4（DR 硬件数） | 无限（仅条目数；须独占整页） |
| 适用 | 冷靶、非 PG 覆盖目标 | 热靶（≥100/s）与 PG 覆盖目标 | 大数量 PG 目标，或需拦截语义的场景 |

**普通模式（CodePage）**——招牌零 exit 钩子。*Primary* 视图把钩子页置为不可执行（数据读写完全正常）；*Secondary* 视图把该页改译到影子副本（目标偏移处 14 字节绝对跳转）。首次取指每核付出一次 NPF，此后每次命中都是纯客户机态翻译，**零 exit**。对影子视图的写访问会 fault 并被转发到真实页——簿记保持一致而调用者永远观察不到影子。fail-loud 拒装门会拒绝 prologue 短于补丁的目标（14 字节窗口内出现控制转移指令 = 安装时拒绝），越权写邻码结构性不可能。

**TRANSPARENT 模式（DR）**——在目标入口线性地址布防硬件执行断点（DR0-3，仅执行）。原页**恒等不动**：任何外部读者（PatchGuard、内核扫描器）任何时候读到的都是原始字节——读/写透明**结构性**成立。每次调用恰 1 次 VM-Exit，无页热约束；实测 2,535 次/秒 #DB exit 持续 600 秒全绿。guest 调试子系统全程裸机等价：自身断点与 TF 单步陷阱忠实投递（`int1`/`ICEBP` 穿透、DR 回读遵循架构语义），guest 活跃调试穿过入口期间钩子静默让位该次调用——裸机行为优先于拦截。你的断点被 MOV DR 影子仿真吸收，同 KVM/VMware 调试影子语义。

**NX-FENCE 模式**——补齐矩阵最后一格：**PG 安全 × 无限容量**。目标页在 Primary 视图置 NX（数据面完全透明），Secondary 视图恒等 RWX；入口取指 fault，引擎改道到跳板，回调返回路径重武装 fence。两视图零工件；稳态成本 = 每次调用 2 exit（入口 fault + 重武装）。选**冷页/页隔离**目标——同页邻函数会放大 exit 流量。

## 🛡️ 引擎能力

- **detour 完整控制权**——回调收到原始参数，可调用原函数（`GnptCallOriginal`）、修改参数或返回值、或整体吞掉这次调用。
- **第 5+ 栈参数转发**——安装时声明目标栈参数个数（≤32），回调收到指向触发栈实参的 `StackArgs` 指针（可读可写，改写随 `GnptCallOriginal` 转发）。
- **版本无关的运行时跳板**——LDE 重定位引擎运行时生成：逐指令解码、RIP-relative 修正、超 ±2GB 远距目标改写为等价 `mov reg, imm64`；不可重定位的 prologue 安装时即拒。执行级单测见 `DbgTools/test_reloc.c`。
- **映像内跳板槽（code cave）**——跳板槽刻在驱动映像自身可执行节的尾碎片里：分支源指向模块内部（正常 LBR 栈形态），地址空间中不出现可执行池页。仅无可用 cave 的映像才回退池。
- **MSR 拦截 API**——每核 MSRPM 位图；架构覆盖范围内任意 MSR 的读伪造/写监控回调（`GnptMsrHookInstall` / `GnptMsrReadReal`）；未挂钩 MSR 零 exit。
- **CPUID 虚拟化隐蔽**——接管核上 SVM 位清零（与 VM_CR 读伪造自洽）、无签名 leaf 归零、max-leaf 永不收缩。全核会话期间任务管理器全程显示"虚拟化： 已禁用"验证通过。
- **NPT 自我隐蔽**——引擎自身页表页（约 2,100 页）在 guest 视图改译到零页；guest 侧扫描器对整套嵌套分页层级读回零，稳态零 exit。
- **TSC 时间轴补偿**——各 exit 路径自行记账开销进 TSC-offset 水位，跨核钳制：时序检测只能看到一致变慢的时钟，永远看不到负增量。
- **调试子系统忠实性**——TF 单步、自设断点、架构化 DR 回读、`int1`/`ICEBP` 软件陷阱全部忠实投递；root 驻留分支不泄漏进 guest LBR 栈。
- **观测体系与构建统辖**——Debug = 完整观测（文件日志 + 事件环 + 蓝屏黑匣子看门狗）；Release = 零日志代码进产物。刻意不用运行期/注册表开关。
- **干净的交付形态**——驱动入口只执行框架生命周期与一个演示钩子；`main.c` 可替换为你自己的逻辑。框架以源码形态集成。

## 📐 零 VM-Exit 钩子的工作原理

```
                Primary 视图                  Secondary 视图
                ┌────────────┐               ┌────────────┐
                │ 恒等映射,   │               │ 钩子页 PTE │
                │ 钩子页 NX  │               │ → CodePage │
                │  (X=0)     │               │ (X=1, W=0) │
                └─────┬──────┘               └─────┬──────┘
                      │ 数据读写透明                │ → 影子副本(CodePage)
   guest ─────────────┴────────────────────────────┴─────────────────
        钩子页首次取指: NPF → 引擎切该核到 Secondary(TLB冲净)
        —— 此后每次命中都是纯翻译, 零陷入
```

钩子触发链（全程客户机态，零 VM-Exit）：

```
调用者 → 目标函数(Secondary视图=CodePage, 目标偏移处14字节绝对跳转)
  → 本hook独享的跳板槽(映像内code cave; mov r10,条目;
    jmp GnptStubEntry)
  → GnptStubEntry: SAVE_ALL → 分发你的回调
      (可 GnptCallOriginal: 经LDE重定位跳板调用原函数——视图无关,
        回调内调用的其他钩子目标正常触发=标准detour语义)
    → RESTORE_ALL
  ← 调用者(RAX = 你回调的返回值)
```

## 🚀 快速开始

安装并启动驱动：

```
sc create GnptHooks type= kernel start= demand binPath= "C:\path\to\GnptHooks.sys"
sc start GnptHooks
```

停止并卸载（全部钩子先被干净移除，随后经 STOP 桥在全部核心关闭 SVM）：

```
sc stop GnptHooks
sc delete GnptHooks
```

调试日志无需任何开关：直接用 **Debug 构建**即获得完整观测；**Release 构建**产物零日志代码。

## 🧩 API 使用

```c
#include "hook.h"

// 你的detour回调: 运行在原函数的线程与IRQL上下文,
// 返回值即钩子函数的返回值。
// StackArgs: 第5+个参数(栈参数)数组, 可读可写——
// 改写后的值随GnptCallOriginal一并转发。
static ULONG64 OnNtClose(PVOID Context,
    ULONG64 Arg1, ULONG64 Arg2, ULONG64 Arg3, ULONG64 Arg4,
    ULONG64* StackArgs)
{
    ULONG64 status = GnptCallOriginal(Arg1, Arg2, Arg3, Arg4);
    return status;   // 也可以伪造——你拥有完整控制权
}

UNICODE_STRING name;
RtlInitUnicodeString(&name, L"NtClose");
GNPT_HOOK Hook = { 0 };
Hook.Target    = MmGetSystemRoutineAddress(&name);  // 参数是PUNICODE_STRING!
Hook.Callback  = OnNtClose;
Hook.Context   = NULL;
Hook.StackArgs = 0;        // 目标第5+栈参数个数
Hook.Flags     = 0;        // 0 / HOOK_TRANSPARENT / HOOK_NXFENCE

GnptHookInstall(&Hook);
// ... 钩子已在全部核心生效 ...
GnptHookRemove(Hook.Target);
```

**契约**（完整纪律清单在 `hook.h`——它才是权威）：

1. 回调运行在原函数的线程与 IRQL 上下文（可达 DISPATCH 级）——只做 IRQL 安全操作（原子操作、无锁环事件、`GnptCallOriginal`）。
2. 调用本钩子的原函数**必须**经 `GnptCallOriginal`；直接调用原入口会在 Secondary 视图下撞入跳转码。
3. **目标选型**：热靶（≳100 次/秒）一律 TRANSPARENT（实测定罪：同函数同流量 152k 次/600s——CodePage 模式产生 DWM 崩溃循环，DR 模式零事件）；PG 覆盖目标用 TRANSPARENT 或 NX-FENCE，禁用普通模式；NX-FENCE 目标不得与任何已有钩子同页（安装即拒）。
4. `GnptHookInstall/Remove/Enumerate` 为单写者设计——调用方自行串行化（专用线程或互斥）。
5. 卸载顺序：关 SVM **之前** `GnptHookRemoveAll`，关 SVM **之后** `GnptHookFreeMemory`——参考 `main.c` 的 `DriverUnload` 标准序列。

## ⚙️ 环境要求

- **CPU**：支持 SVM + 嵌套分页（NPT）+ NRIPS 的 AMD 处理器（启动时检测；缺特性 = 干净拒绝，绝不半接管）
- **操作系统**：Windows 10 x64（Zen 3 移动端与 Zen 5 桌面端已实测；其他世代预期可用——请在你的硬件上验证）
- **虚拟化冲突**：需关闭 Hyper-V、基于虚拟化的安全（VBS）、内存完整性（核心隔离）与 WHP——GnptHooks 必须作为根 hypervisor 运行
- **嵌套测试**：开发期在 VMware 嵌套 SVM 下运行；嵌套环境会失真部分特性位——虚拟机内观察到的异常须先在物理机上复现，再当作 bug 处理
- **测试签名**：执行 `bcdedit /set testsigning on` 开启测试签名，或对驱动进行正式签名
- **构建**：Visual Studio 2022 + Windows Driver Kit（WDK）
- **接管核剂量**（`common.h` 的 `GNPT_TAKE_CORES`）：默认全核接管——CPUID 伪装仅在全核形态下完整。剂量敏感平台（见下）日常开发请降低核数构建，全核会话只留给冷启后的短促验证。

## 🖥️ 平台风险

在 AMD 硬件上运行裸机 hypervisor 之前，请先阅读本节。

**sub-SMM 杀手（静默硬件复位）。** 在部分 AMD 移动平台上（实测：固件已 EOL 的 Cezanne / Zen 3 笔记本），一种稀疏的、发生于 SMM 之下的外部事件（疑似 SMU/EC 类）会在全核 guest 停泊时静默复位整机。签名：硬件级复位、无蓝屏、无 WHEA 记录、无任何日志前兆——驱动完全不在场也可能发生。软件层不可修：`HWCR.SMMLOCK=1` 封死了 SMI 拦截，杀手对 OS 和 VMM 双重不可见。

**剂量敏感型桌面平台。** 在部分桌面硬件上（实测：AM5 / Zen 5），全核 SVM 驻留的行为像一份*可消耗额度*：会话在额度耗尽后死亡——静默复位，或 CLOCK_WATCHDOG_TIMEOUT（挂死核楔死；同一事件的两种外显）。复位本身不重置额度；它只随分钟到小时级的非驻留时间恢复。实验已排除：C-state 深度、负载水平、特定应用程序、以及全部软件可见观测面。低剂量构建在完整测试套件下保持健康。有效缓解：剂量控制 + 会话时长控制。

**受影响平台的操作规程。** 凉机 + 开机后晚些加载 + 默认电源方案 + 短突发：验证与卸载在数分钟内完成；死亡后绝不要立即重启再测（那是复位循环最热的窗口）。实测隔夜断电后的首次凉机运行是最稳定的窗口。

**硬件特性边界**（启动时探测，日志横幅如实报告）：部分 Zen 3 消费级 APU 缺席 PMC/IBS 虚拟化（该平台上 PMU 侧信道无法用硬件闭合）；TSC_DEADLINE 轴换算仅当 LAPIC 实际处于 TSC-deadline 模式时启用；STGI 直通按 SKINIT 特性位门控。

**硬件选型建议。** AMD 微码只能通过 OEM 的 BIOS/AGESA 更新到达消费者。OEM 已停止 BIOS 更新的平台对任何裸机 hypervisor 都是硬风险。优先选择 AGESA 更新节奏活跃的主板。
